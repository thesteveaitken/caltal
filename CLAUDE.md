# CalTal

Personal calorie and macro tracker, shared with a few friends. Not commercial. Mobile-first dark UI.

## Architecture
- **Static files only**: `index.html` (markup), `styles.css`, and plain scripts in `js/` that share globals (no modules). Vanilla JS and CSS, no framework, no build step. Keep it that way.
- **Backend is Supabase only**: Postgres, Google sign-in, and row-level security (RLS). The browser calls Supabase directly through `supabase-js` (pinned CDN script). There is no server code.
- **Guest mode:** there is no sign-in screen. With no session, the app runs as a guest: `sb` is `makeLocalClient()` and a banner asks them to sign in. The stand-in answers the same query calls from `localStorage` (`caltal_guest_v1`); only the standard foods are read from Supabase (anon `select` policy on `foods` where `owner_id is null`). If the app starts using a new query method, add it to the stand-in. On sign-in, `mergeGuestData()` copies the local data into the account (ids kept, idempotent) and clears it only on success. It uses `upsert(..., { onConflict, ignoreDuplicates })` on foods, favourites and log_entries.
- **Hosting:** GitHub Pages, from `main` of `thesteveaitken/caltal`. Live at https://thesteveaitken.github.io/caltal/. Project ref `virurqttoukgzrpdsizs`.
- **Schema:** `supabase/schema.sql` (tables, RLS policies, the `daily_totals` view). Keep it safe to re-run (`if not exists`, `or replace`, `drop policy if exists`). Each `create table` shows the full current shape; a new column goes both in the `create table` and in an `alter table ... add column if not exists` line right under it, so existing databases catch up. Finished one-off scripts live in `supabase/oneoff/`.
- **Standard foods:** `supabase/seed_foods.sql`. Safe to re-run: existing names are skipped.
- **Old backend:** the Google Sheet and Apps Script. Migrated and retired: the web app deployments were archived on 2026-11-17 and the local `AppsScript.gs` was deleted.

## Data model decisions
- `foods.owner_id IS NULL` is a **standard food**, readable by every signed-in user and by signed-out guests (anon `select` policy). Otherwise the food is private to its owner.
- Only user ids in the `admins` table can write standard foods. Anything added in the app is always private (the new-food form's main button is "Save and log 1 serving", with "Save only" under it; the form takes fluid ml, alcohol and creatine g too, in a collapsed "Drinks & supplements" section; a pencil icon in the log sheet corner reopens that form for the user's own foods, and past entries keep their snapshot values). There is no admin UI: maintain standard foods with SQL or the Supabase table editor.
- **Favourites are per user** (`favourites` table) and can point at standard or private foods.
- The food list (`renderFoodList()`) shows up to 8 recently logged foods first ("Recent", from the latest `log_entries` by `created_at`, kept in `recentFoodIds`), then favourites, then everything A-Z; each food appears once, in one list with no section headings (tried and dropped). Search keeps the same order. One-offs never appear (no `food_id`).
- Nutrition is **per serving, as described in the food name** ("1 cup cooked rice"). There are no units or gram fields.
- `log_entries` store **totals** (per-serving x quantity) plus a `food_name` snapshot, so editing or deleting a food never changes history. `food_id` is null for one-offs. Quantity steps by 0.5, minimum 0.5.
- Foods and entries also carry `alcohol` (standard drinks), `fluid_ml` and `creatine_g` (alcohol counts 0 fluid). Entries have a nullable `eaten_at` (when it was eaten; `created_at` is only insert time, and imported history is null). Supplements like creatine are just 0-calorie foods. Values for standard drinks are in `supabase/seed_drinks.sql`.
- The log sheet has a "Time eaten" stepper (native time input plus round -/+ buttons, 30 min steps). It is blank by default on past days (saved as null). Each entry row has a copy-icon "log again" button that inserts a copy stamped with the current time.
- `supabase/oneoff/backfill_fluids_alcohol.sql` is a one-off that sets fluid/alcohol on the admin's own foods by name, then copies fluid, alcohol and creatine onto past log entries from their foods (x quantity) where those are still 0.
- `supabase/oneoff/backfill_eaten_at.sql` is a one-off that sets `eaten_at` from `created_at` for older entries logged the same (US Eastern) day. The sheet import put the sheet's Timestamp into `created_at`, with noon as a placeholder when it had none.
- On Today, 2+ entries of the same food (same `food_id`, or name for one-offs) on a day render as one collapsible group row (`renderEntries()`), anchored at the most recent entry; the row has log-again. No row has a delete button: tapping an entry opens the log sheet, which has "Remove entry", and the toast offers Undo (`restoreEntry()` re-inserts it with the same id).
- `daily_metrics` holds one weigh-in per user per day (`weight_kg`, `source` manual/import/shortcut), own-row RLS, primary key (user_id, date). Always kg; shown in `profiles.units` (lb by default) via `kgTo()` / `toKg()` / `fmtWeight()`. The optional goal weight is `goals.weight_kg`, editable in both the Goals sheet (a normal goal row, saved by "Save goals") and the Weight sheet; sheets are never stacked. The two rows share one set of functions in `js/weight.js` (`GOAL_WEIGHT_ROWS` holds each sheet's element ids and writes both rows' markup into empty containers in `index.html`; `fillGoalWeightRow()`, `setGoalWeightOn()`, `setGoalWeightUnits()`, `readGoalWeight()`, and `readWeight()` for any weight box): 1 decimal in the person's units, stored as kg to 2 decimals (not 1, so pounds round-trip), and a box still showing the stored value saves it as it was. The Weight sheet is only the day's weight, lb/kg, Remove, and the goal (no history list: Trends covers that). The Weight sheet (profile menu, `openWeight(date)`) logs for the viewed day; the Weight Trends card (`drawWeightChart()`) appears once there is a weigh-in or a goal. Its dots are real weigh-ins; its line is a 7-day rolling average in which days with no weigh-in are filled by a straight line between the weigh-ins either side (any gap length, using the nearest weigh-in outside the window at the edges), and it stops at the latest weigh-in. Apple Health sync is a private Shortcut for Steve (ROADMAP section 4, setup in SETUP.md section 6), since a website cannot touch Apple Health: it calls `log_weight()`, a security-definer function the anon role can execute, which finds the user from a personal key in `sync_keys` (SHA-256 hash only, RLS on with no policies) and upserts that day's weight with source 'shortcut'. Keys are made with `supabase/new_sync_key.sql` and, like the secret key, never go in the repo or chat.
- `quick_adds` holds up to 6 buttons per user (slot 0-5, food_id, label up to 10 chars, `QUICK_LABEL_MAX`), own-row RLS; deleting a food removes its button. With no rows the app shows a virtual "Water" button. One tap logs one serving.
- `goals` holds one row per user (calories as a ceiling, protein, fluid_ml, creatine_g), own-row RLS. A null goal means off: protein loses its goal bar, and fluids and creatine disappear from the summary (creatine's Trends card also disappears; Fluids' Trends chart stays, without a goal line). With no row the app uses only a calorie ceiling of 2000, everything else off. Standard supplement foods are in `supabase/seed_supplements.sql`.
- `profiles` holds one row per user (birth_year, sex male/female/other, height_cm, weight_kg, units us/metric, activity, aim), own-row RLS; always stored metric. It is written by the Goals sheet's collapsed "Help me choose" helper (`helperCompute()`), which prefills from it. The helper uses Mifflin-St Jeor x activity (1.2/1.375/1.55/1.725), "Other" averages the sex term (-78) and floors (1,500 / 1,200 / 1,350 cal); aims are lose slowly -10% (protein 2.0 g/kg), lose faster -20% (2.2), maintain (1.6), build muscle +10% (2.0); fluids 35 ml/kg; protein and fluids use the weight for a BMI of 25 when the person is heavier. "Fill in my goals" fills and switches on calories, protein and fluids (never creatine) and saves the profile; only "Save goals" saves goals. Under 18 it refuses. Guests keep the profile in the stand-in and it merges on sign-in if the account has none.
- The Trends tab (ruled sections for calories, protein, fluids, carbs and fat, creatine dots and alcohol) reads the `daily_totals` view; charts are inline SVG drawn by `drawTrendChart()` / `drawDotStrip()`, not a library. `renderTrends()` writes each card's shell (`trendCardShell()`), then hands its parts to one renderer per kind, picked by `trendCardKind()` from `TREND_RENDERERS` (`renderGoalCard`, `renderStackCard`, `renderWeightCard`, `renderCreatineCard`, `renderAlcoholByDay`, `renderAlcoholByWeek`); a new card kind is a new renderer there. Bars: amber counts toward or met a goal, crimson is over the calorie limit, short of a floor goal is a pale bar with a dark 3px cap at the value (`--miss` body, `--miss-cap`; the cap carries the contrast, so missed days stay quiet); today is a dashed outline (unfinished) unless already over or met. Alcohol is by day on the 7-day view and by week (8 weeks) on the 4-week view. Creatine is dots: one row on 7 days, a 4 x 7 grid on 4 weeks (each column a weekday); its header shows days at goal and the current streak (`creatineStreak`, counted back from today or yesterday, regardless of the window).
- `daily_totals` has no rows for days with no entries, so empty days are naturally skipped.
- Accessibility: pinch-zoom stays on (keep inputs at 16px or more so iOS does not zoom on focus); every icon-only button has an `aria-label`; one `:focus-visible` ring for all controls; sheets take focus when they open and hand it back on close (not to text fields); `prefers-reduced-motion` turns transitions off. An axe-core scan of Today, the edit sheet and Trends was clean in both themes (Nov 2026).
- Security lives in RLS, not in the client. Any new table needs RLS enabled and policies written before it is used.

## Rules
- **Keys:** the publishable key (`sb_publishable_...`) is public and lives in `js/core.js`. The secret key (`sb_secret_...`) must **never** go in the app's files, the repo, or chat. It is only for `scripts/.env`.
- **Gitignored, never commit:** `scripts/.env`, `*.csv` and `promote.txt`.
- Check `git status` before committing: this repo is public.
- The Google OAuth consent screen is **In production** (published 2026-11-17), so any Google account can sign in. Its Branding page links the home page, `privacy.html` and `terms.html`; if the site moves to a new address, update those links and the authorized domain there too.
- supabase-js: call other Supabase methods inside `onAuthStateChange` only after a `setTimeout`, to avoid a deadlock.

## Run and deploy
- **Local:** `cd` to the project, run `python3 -m http.server 8000`, open http://localhost:8000. Hard-refresh after edits.
- **Deploy:** commit and push `main`. Pages rebuilds in a minute or two. Pages caches each file for 10 minutes, so right after a deploy a browser can hold a mix of old and new files; a hard refresh fixes it.
- **Smoke test:** `python3 scripts/smoke_test.py` runs one guest-mode session (`scripts/smoke_test.js`) in headless Chrome against `HEAD` and against the working tree, and compares what each rendered and saved. Run it after any change that should not alter behaviour (refactors); every step should say SAME. It does not cover Google sign-in, the guest merge or the desktop layout. When a feature changes the UI on purpose, expect DIFF on the steps it touches, and add steps for new features. `--show STEP` prints a step in full from both runs.
- **Database changes:** edit `supabase/schema.sql`, then run the new SQL in the Supabase SQL editor. There are no migrations tooling or tests.
- **One-off import** (already done): `scripts/migrate_from_sheet.py`. It is standard-library Python and the full steps are in `SETUP.md`.
- **Weight history import:** `scripts/import_health_weight.py <export.zip>` (Apple Health export; dry run unless `--apply`; same `scripts/.env`). Averages each day's weigh-ins, source 'import', never overwrites an existing day. Keep the export outside the repo.

## Where things are
- `index.html`: markup only. It loads `styles.css`, then the scripts at the end of `<body>` in this order (later files use earlier ones at load time, so keep the order):
  - `js/core.js`: Supabase client and keys, shared helpers, shared state (`user`, `foods`, `entries`, `currentDate`...), toast, `must()`.
  - `js/guest.js`: `makeLocalClient()` and `mergeGuestData()`.
  - `js/goals.js`: goals, the Today summary (`renderTotals()`, `renderTally()`), the Goals sheet and its helper, `profile`.
  - `js/weight.js`: weigh-ins, `weightAvgOn()`, the Today weight cell, the Weight sheet.
  - `js/today.js`: loading foods and entries, entry rows, food list and search, quick-adds, the log, food and one-off sheets, the day switcher.
  - `js/trends.js`: the Trends view and its charts.
  - `js/app.js`: profile menu, sheet focus and closing, tabs, auth (`showApp()`), start-up. Loaded last.
- State is global variables, declared in the file that owns them. Each of goals, weight, today and trends has a `reset...State()` that `showApp()` calls when a different person signs in: **new per-user state must be added to its file's reset function**, or one person's data can show for the next. Data access goes through the `must()` helper, which turns Supabase `{data, error}` results into exceptions.
- **Shared helpers** (in `js/core.js`, use these instead of repeating the code): `InvalidField` and `trendsVisible()`; `show(el, on)` to show or hide anything (it sets the `hidden` attribute, and `[hidden] { display: none !important; }` in `styles.css` beats any layout rule; never set `style.display`, and start hidden markup with `hidden`, not an inline style); `$(id)` for `getElementById`; `openSheet(id)` / `closeSheet(id)`; `setSeg(id, isOn)` for `.seg` controls; dates with `ymd()`, `hhmm()`, `dayStart()`, `addDays()`; `NUTRIENTS` (the seven amount columns) with `FOOD_COLS` / `ENTRY_COLS`; `servingOf(food)` and `eatenNow(date)` for one-tap logs; `withBusy(btn, busyText, work)` for save/log/remove buttons (disables the button, swaps its text if `busyText` is given, restores both; the handler keeps its own try/catch inside `work`, and generic failure toasts read "Could not save. Try again." / "Could not log. Try again." / "Could not remove. Try again."); `niceStep()` and `chartDayAxis()` for charts (these two are in `js/trends.js`).
- **Header:** a round profile button (Google photo or initial; a hamburger icon for guests) opens a menu with email, Goals, Weight and Quick-add buttons (all sheets) and Sign out ("Sign in with Google" for guests). Guests also see a one-line amber strip at the top ("Saved on this device only. Sign in to keep it"). Goals state and the summary are in `loadGoals()` / `renderTotals()`.
- **Today summary:** calories so far as a large number ("785 / 2,200", with "1,415 left" or "352 over" beside it), then the **tally** (`renderTally()`, inline SVG redrawn on resize): 20 marks struck in fives reach the calorie goal and take 2/3 of the width, so up to 150% fits on one line; the mark in progress fills from the bottom; past the goal marks use `--danger` after a thin goal marker. With no calorie goal the tally counts against 2,000, stays amber, and has no marker. Under it, the goal grid: goals that are on (protein, fluids, creatine) with a bar, then carbs and fat as plain figures, then a Weight cell for anyone with a weigh-in or goal weight (`weightCellHtml()`, data from `loadDayWeight()`; tapping it opens the Weight sheet for that day, and a small pencil (weighed that day) or plus icon beside "Weight" says so). It shows the day's weigh-in (with the 7-day average under it); else, between two weigh-ins each at most 30 days away, the 7-day average dimmed as "~"; else, up to 14 days after the latest weigh-in, that weight and its age, dimmed; else "Add". The 7-day average is `weightAvgOn()`, shared with the Trends line. Design decisions and colours are in `.impeccable.md`. There is one amber, the logo's `#e8a23d`, in both themes; in light mode it is never used for text (`--accent-text` is ink there) because it is 2:1 on paper.
- `caltal-icon.png`: the app logo on its dark tile. The header draws the tally mark itself as inline SVG in the theme colours; the favicon is inlined separately.
- **Layout:** mobile-first with a bottom tab bar. At 900px and up (one `@media` block at the end of the CSS) the page widens to 1100px, tabs and Sign out move into the header, and Today becomes two independently scrolling columns. From 1100px (full page width) the summary's goal grid is one row however many cells it has (six fit; below that it is 3 columns like phones). If a 7th metric arrives, decide then between two rows and letting people choose what shows. On phones the search box and quick-adds are a band pinned above the tab bar; focusing search opens it full screen (`body.adding`, `enterAdding()` / `exitAdding()`) and hides the quick-adds at once, and reloading entries after a log closes it. In that screen "New food" and "One-off" are two small outlined buttons right under the search box (CSS `order`, so they stay above the keyboard); on desktop they stay a "Not listed?" line under the list. Both prefill their name from the search text. On desktop the quick-adds hide only while the search box has text. The quick-add row has no label ("Quick:" was dropped). The day switcher (`#dateNav`) is moved between the header and the left column by `placeDateNav()` in the script, so keep it as a single element.
- **Sheets:** bottom sheets on paper with a handle; each has a `.sheet-head` whose `aria-label="Close"` button does the cleanup, and tapping outside or pressing Escape clicks it (one Escape closes one layer). The log sheet shows "After this: N cal left/over" (`updateQtyDisplay()`).

Contact is caltalapp@gmail.com. If the app starts storing something new or loading a new outside service, update the policy and its date.
